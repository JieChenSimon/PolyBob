# PolyBob 产品、量化、数据与模拟盘完整性

## Scope

适用于 PolyBob 的产品定位、前后端功能、量化研究、真实外部数据、数据集、Paper
Trading、策略验证、任务推进和交付验收。Kronos 独立参考仓库仍不属于 PolyBob 的修改、
提交、推送、回滚或测试范围。

本约束记录用户对系统的实际目标：PolyBob 是一个以真实交易和盈利能力为最终目标、
以量化分析为核心、真实数据驱动、可重放、可审计的个人交易系统。研究、历史回测、
模拟盘、数据工程和风控都是服务于真实交易决策与执行的验证和保护层，不是最终产品目的。
系统必须持续寻找具有成本后正期望收益的策略，但不得把未经验证的“AI 预测”或装饰性
交易页面冒充盈利能力。

## Hard acceptance criteria

### 1. 产品目标、交易边界与真实性

- 真实交易和可持续盈利能力是最高级产品目标；每项研究、模拟盘、数据和 UI 工作都必须说明
  它如何支持策略发现、盈利验证、风险控制、交易执行或交易复盘，不能以“研究完成”作为最终
  交付终点。
- 系统应在证据充分后为真实交易准备并接入真实 venue，但真实下单仍必须经过 adapter 认证、
  权威账本、组合风控、策略晋级和人工/配置开关；“以真实交易为目标”不等于绕过安全门禁。
- Paper Trading 是真实交易前的长期验证环境，必须使用真实行情、真实信号和真实成本假设，
  并将结果用于判断策略是否有机会在真实交易中盈利。

- Core、Lab、Archive 必须明确分层；实验、预测和旧功能不得伪装成生产交易能力，Paper Trading
  必须明确标示为真实交易前的验证与准备层。
- 所有收益、胜率、Sharpe、回撤、策略有效性和“能赚钱”结论必须标注数据来源、观察时点、
  样本范围、成本假设和验证状态。
- 未配置、未知、过期、降级、数据不足、模型未校准或证据不足时必须显示
  `UNKNOWN`/`DEGRADED`/`BLOCKED`，不能显示为 0、无风险、可交易或生产就绪。
- 系统不得承诺任何标的或策略必然盈利；没有真实、样本外、成本后证据的策略不得晋级交易。
- 任何真实 venue 下单能力在未通过 adapter 认证、账本对账和风险门禁前必须保持关闭；默认只允许
  研究和 Paper Trading。

### 2. 标的和真实世界数据覆盖

- 系统必须支持并区分美股、A 股、BTC、主流加密货币/山寨币以及 BTC 5 分钟研究数据；
  每个标的页面必须保持自己的 symbol/instrument 上下文，不能串显示其他标的数据。
- 真实外部数据必须优先使用 SEC、交易所、行情/订单簿、资金费、公司行动和交易日历等可追溯来源；
  不能用占位符、静态 mock 或合成收益替代真实策略证据。
- 每类数据必须保存为可重复使用的数据集，并记录 source、request、event/effective time、
  observed/fetched time、instrument、数据契约、PIT 等级、price basis 和失败状态。
- 原始响应必须不可变、内容寻址、去重并保存 provenance；规范化数据必须可查询、可重放、可按
  `as_of` 恢复历史观测；重复 provider payload 不得产生重复 observation。
- 网络采集必须具备缓存、断点、重试、退避、超时、限速保护和失败后可恢复行为；限速或连接阻塞
  不能成为放弃数据工程或策略验证的理由，必须降速、缓存、重试或明确记录 UNKNOWN。

### 3. 量化研究与策略有效性

#### 用户收益目标硬门槛

- 对用户纳入实盘候选的每一个标的，目标底线为：经真实数据、真实成交假设、成本后、样本外和可重放证据验证的年化收益不少于 50%，且每个已完成观测月的收益不少于 15%。这两个阈值同时适用，不能用组合平均值、单一幸运月份或未扣成本收益替代。
- 收益目标是晋级验收门槛和优化方向，不是系统可以保证的收益承诺；当历史样本、当前市场或真实模拟盘无法满足时，状态必须为 `NO_EDGE`/`BLOCKED`/`UNKNOWN`，不得通过调参、缩短样本或选择性展示伪造达标。
- 必须逐标的、逐月保存收益、基准、成本、滑点、资金费、交易数、最大回撤和数据覆盖；年化收益与月度收益需同时报告，且明确样本外区间、观察时点和是否正在进行中。
- 任何候选若未达到上述目标，不得进入真实交易权限；系统必须量化未达标原因，提出预注册的受约束候选并重新进行样本外、成本压力、稳定性、回撤和多重检验。

- 每个策略必须明确记录假设、经济机制、方向、适用标的、参数、持有期、手续费、滑点、资金费、
  市场冲击、容量和样本范围。
- 参数选择必须只使用训练数据；评估必须使用真正的 walk-forward、样本外窗口、purge/embargo
  和可交易生效时间，禁止前视、未来价格或事后修正数据泄漏。
- 报告至少包括成本后收益、基准收益、Sharpe、最大回撤、交易数、胜率/盈亏因子、稳定性、
  参数敏感性、不同市场/标的表现和组合层面的相关性、集中度与风险。
- 组合收益优化必须比较简单基准，经过成本压力测试、样本外测试和跨标的稳健性测试；
  “相对基准少亏”不能标记为盈利策略。
- 研究和预测运行必须有唯一 run_id、完整参数、代码版本、输入数据批次/哈希、模型/ tokenizer
  版本或哈希、结果和可重放 manifest；缺 lineage、脏代码、样本不足或无法复现的结果不得晋级。
- 预测必须在到期后用真实结果自动结算，并与 naive 基线比较；样本不足或尚未结算必须返回
  `UNKNOWN`，不能给出确定性收益结论。

### 4. Paper Trading / 模拟盘

- 必须提供用户可操作的前端模拟盘，类似专业交易平台的研究型 paper workspace，而不是只有后端
  API 或静态报表。
- 用户必须能在自己的标的上创建运行、选择真实策略、设置 paper 资金和配置，启动/暂停/停止运行，
  查看实时刷新状态，并长期运行积累证据。
- 模拟盘行情必须来自真实外部实时/近实时数据；策略必须使用真实信号链路；行情不可用、过期或
  策略信号未知时不得伪造成交或使用静态价格。
- 模拟执行必须记录并计算真实假设下的手续费、滑点、市场冲击、资金费、成交延迟、部分成交、
  限价单、IOC/FOK、撤单竞态和流动性不足。
- 模拟盘必须展示持仓、现金、NAV/权益、未实现/已实现 PnL、收益、回撤、费用、资金费、成交明细、
  风险门禁和审计账本；所有数字必须能从持久化记录重放得到。
- Paper fill 必须接入权威 execution ledger，fill、cash、position、fee 和 realized PnL 必须原子、
  幂等、append-only，并支持重启恢复、projection verification 和 reconciliation。
- 模拟盘结果用于真实交易前的盈利证据和风险验证，但不能自动获得真实交易权限；样本量不足、
  成本后无 edge 或晋级门禁未通过时必须显示 `LAB_ONLY`/`NO_EDGE`/`UNKNOWN`，并阻断真实下单。

### 5. 前端 UI/UX

- 页面必须围绕真实操作任务设计：Daily Brief、市场观察、标的研究、策略证据、Paper Trading、
  Execution、Risk Ops、Settings 各自有清晰职责。
- 资产终端必须采用统一专业工作台结构和主题：标的队列、中心行情/研究、右侧风险与证据；不能出现
  白色外壳套深色终端、重复导航、廉价营销卡片或装饰性 hero。
- 当前选中标的必须在 URL、队列、中心、图表、盘口、研究结论、风险面板和交易动作中保持一致；
  不存在于最新 provider snapshot 的标的必须显示不可用/未知或同步到明确候选，不能悄悄替换成另一个标的。
- 所有行情与策略页面必须展示来源、freshness、PIT/观察时间、数据状态、模型版本、基准和校准/证据状态。
- 桌面和移动端必须可用；移动端优先显示选中标的、核心结论和操作，不得强迫用户先浏览长列表。
- 中英文切换必须覆盖导航、标题、状态、空状态、错误、操作按钮和指标；除 ticker、协议名、来源名外不得
  在核心工作流中无意混用语言。
- 每个新增/修改路由必须有前端测试、生产构建和真实浏览器冒烟/截图验收；截图不能替代可重复测试。

### 6. 持续推进、任务和质量闭环

- 用户要求“全部继续/不要停”时，必须继续检查任务看板，逐项处理 TODO、DOING 和 PARTIAL；不能只
  完成一批后把剩余任务隐去或宣称全部完成。
- 每项任务必须有明确验收条件、依赖、证据、状态和关联 Git trailer；未运行、UNKNOWN、接口存在或
  文档声称不能替代真实验收。
- 修改前必须检查当前 Git 状态；涉及代码的工作必须按 Development Control 建任务/复用任务、测试、
  校验、提交并在用户要求时推送。不能 reset、force-push、清理用户文件或绕过任务状态机。
- 任何失败必须形成证据链：复现、根因、修复、回归测试、残余风险；外部数据失败只能导致降级/未知，
  不能通过硬编码或静态 fallback 把失败伪装成成功。
- 最终交付必须同时报告已完成、已验证但未晋级、仍未完成和阻塞项；不能用“目标是赚钱”替代已证明的
  策略有效性。

## Rejection conditions

- 合成数据、占位标的、静态价格或未经声明的 mock 被用于宣称策略盈利。
- 未扣成本/资金费/滑点的回测被当作可交易收益。
- 样本内优化、前视数据、未来价格、事后修正数据或不可重放结果进入晋级结论。
- 模拟盘没有真实行情、真实信号、持仓/PnL/回撤/审计链路，却被描述为可验证自动化交易。
- Paper Trading 或 Lab 功能绕过 promotion gate、risk gate、ledger 或未知状态保护。
- 页面显示的标的、数据状态、策略状态与后端实际状态不一致。
- 任务只完成部分验收却标记 done，或测试/build/浏览器验收未实际运行却声称通过。

## Required validation

根据变更范围，至少运行：

- `uv run --locked python scripts/dev_control.py board`
- `uv run --locked python scripts/dev_control.py validate`
- 相关 Python 测试；必要时 `uv run --locked pytest -q`
- `cd apps/dashboard && npm run test -- --run`
- `cd apps/dashboard && npm run build`
- API 启动/路由契约和真实数据 smoke test（若涉及 provider，结果必须区分 available/degraded/unknown）
- 受影响 UI 路由的桌面/移动浏览器冒烟与截图复核
- 量化变更的真实历史数据、成本后、样本外、稳定性和组合风险报告
