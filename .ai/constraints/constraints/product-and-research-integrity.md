# PolyBob 产品、量化、数据与模拟盘完整性

## Scope

适用于 PolyBob 的产品定位、前后端功能、量化研究、真实外部数据、数据集、Paper
Trading、策略验证、任务推进和交付验收。Kronos 独立参考仓库仍不属于 PolyBob 的修改、
提交、推送、回滚或测试范围。

本约束记录用户对系统的实际目标：PolyBob 是一个以真实交易和盈利能力为最终目标、
以量化分析为核心、真实数据驱动、可重放、可审计的个人交易系统。研究、历史回测、
模拟盘、数据工程和风控都是服务于真实交易决策与执行的验证和保护层，不是最终产品目的。
系统必须持续寻找具有成本后正期望收益的策略，但不得把未经验证的“AI 预测”或装饰性
交易页面冒充盈利能力。

用户需求的规范化追踪见
[`docs/USER_REQUIREMENTS_TRACEABILITY_2026-08-25.md`](../../../docs/USER_REQUIREMENTS_TRACEABILITY_2026-08-25.md)。
该文档只做需求到任务、验收和证据的索引；任务状态和 Git 事实仍以 Development Control 为准。

## Hard acceptance criteria

### 1. 产品目标、交易边界与真实性

- 真实交易和可持续盈利能力是最高级产品目标；每项研究、模拟盘、数据和 UI 工作都必须说明
  它如何支持策略发现、盈利验证、风险控制、交易执行或交易复盘，不能以“研究完成”作为最终
  交付终点。
- 系统应在证据充分后为真实交易准备并接入真实 venue，但真实下单仍必须经过 adapter 认证、
  权威账本、组合风控、策略晋级和人工/配置开关；“以真实交易为目标”不等于绕过安全门禁。
- Paper Trading 是真实交易前的长期验证环境，必须使用真实行情、真实信号和真实成本假设，
  并将结果用于判断策略是否有机会在真实交易中盈利。

- Core、Lab、Archive 必须明确分层；实验、预测和旧功能不得伪装成生产交易能力，Paper Trading
  必须明确标示为真实交易前的验证与准备层。
- 所有收益、胜率、Sharpe、回撤、策略有效性和“能赚钱”结论必须标注数据来源、观察时点、
  样本范围、成本假设和验证状态。
- 未配置、未知、过期、降级、数据不足、模型未校准或证据不足时必须显示
  `UNKNOWN`/`DEGRADED`/`BLOCKED`，不能显示为 0、无风险、可交易或生产就绪。
- 系统不得承诺任何标的或策略必然盈利；没有真实、样本外、成本后证据的策略不得晋级交易。
- 任何真实 venue 下单能力在未通过 adapter 认证、账本对账和风险门禁前必须保持关闭；默认只允许
  研究和 Paper Trading。

### 2. 标的和真实世界数据覆盖

- 系统必须支持并区分美股、A 股、BTC、主流加密货币/山寨币以及 BTC 5 分钟研究数据；
  每个标的页面必须保持自己的 symbol/instrument 上下文，不能串显示其他标的数据。
- 真实外部数据必须优先使用 SEC、交易所、行情/订单簿、资金费、公司行动和交易日历等可追溯来源；
  不能用占位符、静态 mock 或合成收益替代真实策略证据。
- 每类数据必须保存为可重复使用的数据集，并记录 source、request、event/effective time、
  observed/fetched time、instrument、数据契约、PIT 等级、price basis 和失败状态。
- 原始响应必须不可变、内容寻址、去重并保存 provenance；规范化数据必须可查询、可重放、可按
  `as_of` 恢复历史观测；重复 provider payload 不得产生重复 observation。
- 网络采集必须具备缓存、断点、重试、退避、超时、限速保护和失败后可恢复行为；限速或连接阻塞
  不能成为放弃数据工程或策略验证的理由，必须降速、缓存、重试或明确记录 UNKNOWN。

### 2A. 全链路现实数据与真实过程硬约束

- “所有数据都必须真实”是全局硬门禁：凡是用于行情展示、特征计算、信号生成、回测、样本外
  评估、模拟盘成交、PnL、风险、策略比较、收益目标或 Promotion 的输入，必须来自可追溯的
  现实世界观测或现实交易系统记录，包括但不限于交易所行情/资金费/订单簿、SEC/公司披露、
  A 股/美股行情、链上数据、宏观数据、交易日历、真实账户/模拟成交和费用规则。
- 每个现实数据集必须记录 provider、接口或文件来源、请求时间、事件时间、观察时间、原始响应
  或内容哈希、schema、单位、时区、instrument、PIT/as-of 语义和失败状态；只有“看起来像市场
  数据”而没有来源链的文件一律不得进入策略证据。
- “所有过程都必须真实”同样是硬门禁：研究必须真实执行数据读取、特征生成、信号、执行延迟、
  手续费、滑点、市场冲击、资金费、持仓、现金、权益和账本结算；不能用静态报表、手工填数、
  固定收益、随机数或合成成交替代真实过程。
- 合成数据只允许用于单元测试、属性测试、已知答案校准、故障注入和演示 UI 状态；必须显式标记
  `synthetic_test_only`，不得与真实数据混合，也不得用于任何收益、胜率、Sharpe、回撤、策略
  有效性、Promotion 或真实交易权限结论。
- 真实数据不可用、字段缺失、时间戳不明、来源无法验证、过程未实际运行或结果无法重放时，必须
  返回 `UNKNOWN`/`DEGRADED`/`BLOCKED`，不能用 0、上一值、均值、静态缓存或合成值补齐后继续
  宣称有效；缓存只有在其 provenance、TTL、PIT 和可重放性完整时才可作为现实数据的本地副本。
- 报告和前端必须把 `real_data_only`、每个数据源、每个过程阶段和是否使用合成测试数据明确展示；
  “测试通过”仅代表代码路径通过，不能被解释成真实策略盈利证据。

### 3. 量化研究与策略有效性

#### 用户收益目标硬门槛

- 对用户纳入实盘候选的每一个标的，目标底线为：经真实数据、真实成交假设、成本后、样本外和可重放证据验证的年化收益不少于 50%，且每个已完成观测月的收益不少于 15%，胜率超过 80%。这三个阈值同时适用，不能用组合平均值、单一幸运月份、未扣成本收益或少量高胜率交易替代。
- 收益目标是晋级验收门槛和优化方向，不是系统可以保证的收益承诺；当历史样本、当前市场或真实模拟盘无法满足时，状态必须为 `NO_EDGE`/`BLOCKED`/`UNKNOWN`，不得通过调参、缩短样本或选择性展示伪造达标。
- 必须逐标的、逐月保存收益、基准、成本、滑点、资金费、交易数、最大回撤和数据覆盖；年化收益与月度收益需同时报告，且明确样本外区间、观察时点和是否正在进行中。
- 必须逐标的保存成本后胜率、胜率分母、闭合交易数和胜率置信区间；闭合交易不足或胜率未超过 80% 时，候选不得进入 Promotion。
- 任何候选若未达到上述目标，不得进入真实交易权限；系统必须量化未达标原因，提出预注册的受约束候选并重新进行样本外、成本压力、稳定性、回撤和多重检验。

- 每个策略必须明确记录假设、经济机制、方向、适用标的、参数、持有期、手续费、滑点、资金费、
  市场冲击、容量和样本范围。
- 参数选择必须只使用训练数据；评估必须使用真正的 walk-forward、样本外窗口、purge/embargo
  和可交易生效时间，禁止前视、未来价格或事后修正数据泄漏。
- 报告至少包括成本后收益、基准收益、Sharpe、最大回撤、交易数、胜率/盈亏因子、稳定性、
  参数敏感性、不同市场/标的表现和组合层面的相关性、集中度与风险。
- 组合收益优化必须比较简单基准，经过成本压力测试、样本外测试和跨标的稳健性测试；
  “相对基准少亏”不能标记为盈利策略。
- 单个策略、特征、过滤器或执行改进未达到最终收益/胜率门槛，不等于必须丢弃：只要在真实数据上有可重复的边际改善、风险降低或成本改善，必须登记为 `CANDIDATE_COMPONENT`，保存独立贡献、适用域、相关性和失败边界，再进入预注册组合验证；只有组合后的全部门禁通过才可 Promotion。
- 组合优化必须先冻结组件、权重、入场/退出规则和风险预算；不得用验证区结果反选组件或权重，不得机械叠加多个失败信号。组件单独未达标时状态应为 `NOT_PROMOTABLE_AS_STANDALONE`，但仍保留为可审计的组合研究输入。
- 研究和预测运行必须有唯一 run_id、完整参数、代码版本、输入数据批次/哈希、模型/ tokenizer
  版本或哈希、结果和可重放 manifest；缺 lineage、脏代码、样本不足或无法复现的结果不得晋级。
- 预测必须在到期后用真实结果自动结算，并与 naive 基线比较；样本不足或尚未结算必须返回
  `UNKNOWN`，不能给出确定性收益结论。

### 4. Paper Trading / 模拟盘

- 必须提供用户可操作的前端模拟盘，类似专业交易平台的研究型 paper workspace，而不是只有后端
  API 或静态报表。
- 用户必须能在自己的标的上创建运行、选择真实策略、设置 paper 资金和配置，启动/暂停/停止运行，
  查看实时刷新状态，并长期运行积累证据。
- 模拟盘行情必须来自真实外部实时/近实时数据；策略必须使用真实信号链路；行情不可用、过期或
  策略信号未知时不得伪造成交或使用静态价格。
- 模拟执行必须记录并计算真实假设下的手续费、滑点、市场冲击、资金费、成交延迟、部分成交、
  限价单、IOC/FOK、撤单竞态和流动性不足。
- 模拟盘必须展示持仓、现金、NAV/权益、未实现/已实现 PnL、收益、回撤、费用、资金费、成交明细、
  风险门禁和审计账本；所有数字必须能从持久化记录重放得到。
- Paper fill 必须接入权威 execution ledger，fill、cash、position、fee 和 realized PnL 必须原子、
  幂等、append-only，并支持重启恢复、projection verification 和 reconciliation。
- 模拟盘结果用于真实交易前的盈利证据和风险验证，但不能自动获得真实交易权限；样本量不足、
  成本后无 edge 或晋级门禁未通过时必须显示 `LAB_ONLY`/`NO_EDGE`/`UNKNOWN`，并阻断真实下单。

### 5. 前端 UI/UX

- 页面必须围绕真实操作任务设计：Daily Brief、市场观察、标的研究、策略证据、Paper Trading、
  Execution、Risk Ops、Settings 各自有清晰职责。
- 资产终端必须采用统一专业工作台结构和主题：标的队列、中心行情/研究、右侧风险与证据；不能出现
  白色外壳套深色终端、重复导航、廉价营销卡片或装饰性 hero。
- 当前选中标的必须在 URL、队列、中心、图表、盘口、研究结论、风险面板和交易动作中保持一致；
  不存在于最新 provider snapshot 的标的必须显示不可用/未知或同步到明确候选，不能悄悄替换成另一个标的。
- 所有行情与策略页面必须展示来源、freshness、PIT/观察时间、数据状态、模型版本、基准和校准/证据状态。
- 桌面和移动端必须可用；移动端优先显示选中标的、核心结论和操作，不得强迫用户先浏览长列表。
- 中英文切换必须覆盖导航、标题、状态、空状态、错误、操作按钮和指标；除 ticker、协议名、来源名外不得
  在核心工作流中无意混用语言。
- 每个新增/修改路由必须有前端测试、生产构建和真实浏览器冒烟/截图验收；截图不能替代可重复测试。

### 6. 持续推进、任务和质量闭环

- 用户要求“全部继续/不要停”时，必须继续检查任务看板，逐项处理 TODO、DOING 和 PARTIAL；不能只
  完成一批后把剩余任务隐去或宣称全部完成。
- 每项任务必须有明确验收条件、依赖、证据、状态和关联 Git trailer；未运行、UNKNOWN、接口存在或
  文档声称不能替代真实验收。
- 修改前必须检查当前 Git 状态；涉及代码的工作必须按 Development Control 建任务/复用任务、测试、
  校验、提交并在用户要求时推送。不能 reset、force-push、清理用户文件或绕过任务状态机。
- 任何失败必须形成证据链：复现、根因、修复、回归测试、残余风险；外部数据失败只能导致降级/未知，
  不能通过硬编码或静态 fallback 把失败伪装成成功。
- 最终交付必须同时报告已完成、已验证但未晋级、仍未完成和阻塞项；不能用“目标是赚钱”替代已证明的
  策略有效性。

### 7. Agent 协作规模与适用性

- 默认使用单 Agent 完成连续的分析、实现、测试和集成；不得因为“全部继续”而机械建立团队。
- 只有当任务存在至少两个互相独立、且并行审查能显著降低量化/数据/执行风险的子问题时，才允许使用
  Agent team。
- Agent team 最多 3 个成员；每个成员必须有不重叠的职责、明确输入和结构化交接结果。
- 强耦合编码、数据库迁移、前后端联调、测试修复和最终提交必须由主 Agent 统一完成，不能拆成多个
  Agent 同时写同一组文件。
- 团队结果必须先去重和核对证据，再决定是否修改；重复意见、静态猜测或未运行的审查不能作为验收证据。

### 8. 本地资源与并发运行

- 长时间研究、回放和数据物化必须优先使用多核并发，但默认总 CPU 预算不超过本机逻辑 CPU
  容量的 60%；worker 数、数值库线程数和批量大小必须显式受控，不能让单个 Python 进程无界满载。
- 资源预算是运行策略，不是无条件自动停止：正常运行且实际资源仍在预算内时继续；只有持续超预算并
  明确影响交互/API/系统稳定性时，才记录证据并由主 Agent 判断降并发、排队或暂停。
- 所有并发研究任务必须可恢复、可重放、可审计；worker 崩溃、限速或资源不足只能产生明确的
  `DEGRADED`/`UNKNOWN` 结果，不能生成伪造的完整收益报告。

### 8A. 数据集、小文件与日志生命周期

- 数据落盘必须按“不可变原始证据、规范化可查询数据、短期缓存、回放临时物、运行日志”分层；
  不得把每次请求、每个事件或每个小批次无期限写成独立小文件。
- 原始 provider 响应可以内容寻址保留以支持 provenance、去重和重放，但必须有 manifest、来源、
  请求、哈希、观察时间和保留级别；相同内容不得产生重复 raw artifact 或重复 manifest 事实。
- 规范化数据必须优先使用按数据集/资产域/时间分区的 Parquet（或等价 columnar 格式），批量合并、
  压缩并设置目标文件大小；查询层不得依赖数万级 KB/MB 小文件才能完成一次研究。
- 数据维护必须提供 dry-run inventory、重复检测、合并压缩、校验和原子替换流程；未经校验不得删除
  原始证据、PIT 版本、manifest 或审计账本。清理必须按明确的 dataset/TTL/状态范围执行，禁止宽泛递归删除。
- HTTP 响应缓存、模型缓存和 UI/测试产物必须有命名空间、内容哈希或请求键、TTL/容量上限和清理状态；
  缓存不得被研究报告当作唯一事实源，也不得无限累积。
- 回放 SQLite 的 `-wal`/`-shm`、临时数据库、checkpoint 和中间结果必须有 run_id、状态、进度和
  finally 清理；成功完成、取消和异常退出都必须可恢复且不留下无主临时物。需要长期审计的 ledger
  必须迁移到明确的 archive，而不是留在临时目录。
- 应用和研究日志必须结构化（至少时间、级别、组件、run_id/request_id、事件和错误分类），默认不在
  热循环逐事件输出 INFO；必须使用轮转/按天分片、压缩、保留期限、大小上限和采样/限频，敏感 payload
  和重复堆栈不得无限复制。日志清理不能删除审计账本或唯一的失败证据。
- 每次数据物化、缓存清理、临时物清理和日志轮转都必须输出可审计的计数、字节数、哈希/manifest 变化、
  保留/删除原因和验证结果；发现未知来源、哈希冲突或校验失败时必须 fail closed 并标记 `UNKNOWN`。

### 9. 全标的、全资产域验证

- 候选标的宇宙不得只靠手工固定清单：系统必须能从本地真实数据按训练窗口自动发现候选，记录扫描总量、覆盖、成交活跃度、回撤事件、排除原因和 selection cutoff，并冻结清单后再做 OOS；不得用 OOS 收益反选标的。
- 深回撤策略的适用宇宙必须按低回撤核心资产、高波动成长/周期、A 股和加密等分层；某标的没有 50% 回撤时只能标为“不适用/UNKNOWN”，不得将其当作该策略失败，也不得把它从全系统标的覆盖中静默移除。
- 研究、回测和模拟盘验收的最小单位是“资产域 × 标的 × 策略”，不是只验证一个代表性标的。
  当前至少覆盖 A 股、美股、BTC 现货/5 分钟场景和山寨币；每个域内配置的每一个标的都必须单独
  运行真实数据、成本后成交、样本外、逐月收益、回撤、稳定性和风险门禁。
- BTC-5m、单个股票或任何其他标的的结果不得外推到其他标的，也不得用单一标的的盈利结果宣称
  全系统有效。任何未运行或数据不足的标的必须明确标为 `UNKNOWN`/`NO_EDGE`。
- 逐标的收益目标（年化至少 50%、每个完整月至少 15%）必须在每个标的上分别通过；组合层验证
  只能作为额外门禁，不能替代逐标的门禁。
- 任务看板、研究报告、Promotion Board 和前端模拟盘必须能按资产域和标的追踪证据、失败原因、
  数据覆盖、策略版本和最后一次验证时间。

## Rejection conditions

- 任一生产策略、收益报告、模拟盘结论或 Promotion 证据使用未标注的合成/占位/静态数据，或
  使用没有 provider、时间语义、单位和 provenance 的不可验证数据。
- 任一真实过程被手工填数、固定收益、随机成交、静态价格或未声明 mock 替代，仍被描述为真实
  回测、真实模拟盘或可赚钱证据。
- 合成数据、占位标的、静态价格或未经声明的 mock 被用于宣称策略盈利。
- 未扣成本/资金费/滑点的回测被当作可交易收益。
- 样本内优化、前视数据、未来价格、事后修正数据或不可重放结果进入晋级结论。
- 模拟盘没有真实行情、真实信号、持仓/PnL/回撤/审计链路，却被描述为可验证自动化交易。
- Paper Trading 或 Lab 功能绕过 promotion gate、risk gate、ledger 或未知状态保护。
- 页面显示的标的、数据状态、策略状态与后端实际状态不一致。
- 任务只完成部分验收却标记 done，或测试/build/浏览器验收未实际运行却声称通过。
- 将原始数据、审计账本、PIT 版本或失败证据与缓存/临时文件混为一谈，直接批量删除或覆盖。
- 以数万小文件、无 TTL 的响应缓存、无轮转的日志或无主 SQLite/WAL 作为长期运行的默认落盘方案。
