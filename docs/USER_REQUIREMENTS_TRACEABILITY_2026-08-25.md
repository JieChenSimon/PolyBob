## 文档用途

这份文档把当前对话上下文中已经提出的产品、量化、数据、模拟盘、前端、治理和安全要求，
规范化为可追踪条目。每条记录都连接到一个或多个 PolyBob Development Control 任务，并记录
当前状态、验收证据和未完成原因。

这是“需求追踪账本”，不是第二个任务看板：任务状态和 Git 提交仍以 `tasks/items/*.yml`、
`dev_control board` 和真实提交为准。此处不把“代码存在”“文档声称”“尚未运行”误记为完成。

本账本覆盖当前任务可见的历史对话内容；它是按需求归一化的记录，不伪称为逐字聊天转录。
若后续对话新增需求，必须新增 `R-xxx`，并同时建立或复用任务、验收条件和证据链接。

## 状态定义

| 状态 | 含义 |
|---|---|
| DONE | 需求的验收条件已全部完成，并有测试/报告/Git 证据 |
| PARTIAL | 已有可运行实现或部分证据，但仍有验收条件未完成 |
| UNKNOWN | 真实数据、样本量、PIT、归因或验证尚不足，系统必须保持未知 |
| BLOCKED | 存在已记录且尚未解除的外部/数据/依赖阻塞 |
| NOT_STARTED | 尚未开始或只有规划 |

## 与任务看板的核对规则

1. 每个 `PARTIAL`、`UNKNOWN` 或 `BLOCKED` 需求必须至少连接一个未完成任务，或在任务的
   `why/checks` 中明确其残余原因。
2. 任务只有在全部 checks 完成、测试/报告/Git trailer 存在并通过 `dev_control validate`
   后，才可以把对应需求改为 `DONE`。
3. `UNKNOWN` 不是失败数据的零值，也不是“尚未查看”；必须保留来源、覆盖、PIT、样本量、
   失败原因和下一步证据。
4. 若需求被实现但未进行浏览器截图、真实数据回放、成本后/OOS/稳定性或组合门禁，保持
   `PARTIAL`/`UNKNOWN`，不得因代码已合并而提前关闭。
5. 每轮模拟盘策略迭代都应产出：逐标的 equity/PnL 曲线、成本与回撤、特征权重快照、
   模型贡献、结果关联、样本量/置信度、数据来源和 run lineage。
